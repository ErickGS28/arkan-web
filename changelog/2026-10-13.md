## 3. Migración del frontend a Vercel

El frontend es **Astro en modo SSR** (`output: 'server'`), antes con el adaptador
de Node para correr en contenedor. Para desplegar serverless sin VPS:

- Se reemplazó **`@astrojs/node` → `@astrojs/vercel@^8`** (la v8 es la compatible
  con Astro 5; la v11 exige Astro 7).
- `astro.config.mjs` ahora usa `adapter: vercel()`, manteniendo `output: 'server'`.
- Se agregó `.vercel/` al `.gitignore`.
- `npm run build` verificado: compila sin errores y genera la salida de Vercel.
- Commit: `chore: migrate Astro adapter from Node to Vercel for serverless deploy`.
- Deploy en Vercel conectado al repo de GitHub (deploy automático por push a `main`).

> El `Dockerfile` viejo (Node/VPS) se dejó en el repo; ya no se usa con Vercel.
> Puede eliminarse más adelante si se quiere limpiar.

## 6. Pendiente: reconectar el backend

### Qué necesita el backend (`arkan-service`, NestJS)
- **Base de datos:** MySQL (TypeORM + `mysql2`).
- **Auth:** JWT / sesiones. Nota del changelog previo: las **sesiones son en
  memoria** y se pierden en cada redeploy → conviene persistirlas (DB/Redis).
- **Almacenamiento de archivos:** Cloudflare R2 (SDK de S3) para imágenes de
  marcas y blog.
- **IA de blog:** Google Gemini (`GEMINI_API_KEY`, `GEMINI_MODEL`) — key solo en
  el servidor, nunca en el navegador.
- Variables de entorno de referencia en `arkan-service/service-arkan/.env.example`.

### Opciones de despliegue del backend (gratis, sin VPS)
1. **Más fiel y rápido (recomendado para reactivar):** NestJS tal cual en
   **Render** o **Railway** + **MySQL gratis** (Railway / Aiven / PlanetScale).
   Cambia muy poco código.
2. **Supabase (PostgreSQL):** requiere cambiar el dialecto de TypeORM
   (`mysql` → `postgres`) y la cadena de conexión, y probar entidades/migraciones.
   A cambio, da Postgres + storage + auth gratis en un solo lugar.

### Pasos previstos cuando se reconecte
- [ ] Desplegar `arkan-service` en la plataforma elegida.
- [ ] Levantar la base de datos y restaurar/crear el esquema (y datos si hay respaldo).
- [ ] Reapuntar en Hostinger el `A api → <IP/host del nuevo backend>` (o CNAME).
- [ ] Configurar variables de entorno en el backend (DB, JWT, R2, Gemini).
- [ ] Ajustar **CORS** del backend para permitir `https://arkangroup.mx`.
- [ ] Verificar end-to-end: login, blog (incl. generación IA), encuestas, marcas.

### Mejora pendiente de código (opcional, no bloquea)
- La URL del backend `https://api.arkangroup.mx` está **hardcodeada en ~19 lugares**
  del frontend. Convendría centralizarla en una variable de entorno
  (`PUBLIC_API_URL`) para futuros cambios de dominio del backend.
- `npm install` reportó vulnerabilidades heredadas (varias high/critical).
  Revisar con `npm audit` en una sesión aparte.
